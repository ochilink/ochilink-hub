# Activate all Ochilink Hub sections

This branch implements the seven requested sections using the original login/admin stylesheet and layout. It adds controls within those sections. It does not replace the original sidebar, cards, tables, themes or app modal.

## Rollout order

1. Run database/migrations/003_complete_hub.sql in the same Neon database. The migration is transactional/repeatable, adds tables/columns/indexes and preserves existing accounts and records. Existing previews can continue using the expanded schema.
2. Configure the environment variables below in Vercel. Keep existing DATABASE_URL/POSTGRES_URL and RATE_LIMIT_SECRET. Test credentials must be scoped to Preview; live Stripe credentials belong only in Production after testing.
3. Deploy the codex/complete-hub-sections branch to Preview. The earlier working branch remains unchanged.
4. Configure a test Stripe webhook against this new deployment. Ensure the endpoint is reachable by Stripe; Vercel deployment protection can block provider requests. Verify delivery in Stripe before claiming payments are active.
5. Follow the acceptance checks below. Merge the original foundation PR first, then this feature PR, after review and testing. No production merge is performed by this implementation.

## Vercel environment variables

| Name | Required for | Value source |
| --- | --- | --- |
| APP_ENCRYPTION_KEY | MFA, encrypted email/reset payloads | Generate 32 random bytes as 64 hex characters locally. Retain a secure backup; changing this value invalidates existing encrypted secrets/payloads. |
| PUBLIC_SITE_URL | Reset/payment links and Stripe redirects | Exact HTTPS origin used for this environment; no path/query/fragment. |
| RESEND_API_KEY | Transactional emails | Your Resend sending API key. |
| MAIL_FROM | Transactional emails | Sender on a domain you verified in Resend, for example Ochilink <your-verified-address>. |
| NOTIFICATION_EMAIL | Optional admin request notifications | Your chosen private recipient address. No address is guessed by the code. |
| STRIPE_SECRET_KEY | Checkout | Test-mode secret key from the connected Ochilink Stripe sandbox. |
| STRIPE_WEBHOOK_SECRET | Verified payment/refund updates | Signing secret for this deployment's specific Stripe webhook endpoint. |
| CRON_SECRET | Authenticated background maintenance | Generate a separate random secret locally. |

Generate private keys locally in PowerShell, one command at a time:

    node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"

Run it separately for APP_ENCRYPTION_KEY and CRON_SECRET. Do not paste values into chat, commit them, or share screenshots revealing them.

Connecting the ChatGPT Stripe plugin does not populate server credentials in Vercel. The connected account was confirmed as Ochilink, test mode. No real charge, refund, product creation or live account change was performed during implementation.

## Stripe webhook

Endpoint:

    https://YOUR-DEPLOYMENT/api/stripe-webhook

Events:

- checkout.session.completed
- checkout.session.async_payment_succeeded
- charge.refunded

The endpoint reads raw bytes and verifies Stripe's signature. Unsigned/tampered bodies are rejected. Event IDs are stored transactionally for replay protection. A success-page redirect never marks a consultation paid. Quotes come from the database and are not accepted from the visitor. Pending checkout sessions are invalidated before changing a quote or rotating payment links. Verified refunds update recorded payment state; partial refunds reduce the paid-revenue total. Refund initiation remains in the Stripe Dashboard, not an unconfirmed button in Ochilink.

A payment link is generated by an authenticated administrator for a positive unpaid quote, expires after seven days, and carries an opaque fragment token. Creating a new link invalidates the earlier token and expires pending checkout sessions. Card details are collected by Stripe-hosted Checkout, never Ochilink. Test-mode credentials must be used for acceptance tests.

## What each section now does

- Analytics: a public privacy choice controls anonymous view/click/scroll collection. Do Not Track and Global Privacy Control suppress tracking. Admin pages, forms, query strings, link tokens, raw IP addresses and typed content are excluded. Only the public homepage is tracked. View events are deduplicated per random session/day/path. The existing Analytics tabs use real heatmap counts, scroll depth and page views for the last 30 days; zero/no-data states are honest.
- Recovery: Forgot opens a reset form within the original login panel. Known/unknown accounts receive the same response. Reset tokens are hashed, expire in 30 minutes and work once. Reset invalidates other tokens and all sessions; existing MFA stays enabled. Full feature setup requires the encryption key, canonical origin and email sender settings.
- MFA: Settings supports password-confirmed TOTP enrollment, authenticator URI/manual secret, verification before enable, eight one-time recovery codes, and password-plus-code disable. Codes are compatible with standard authenticator apps. Secrets are encrypted with AES-256-GCM; recovery codes are hashed. The same TOTP step cannot be reused. Login asks for a code only after the password passes. Enrollment/disable revokes other sessions while retaining the current password/code-verified session. Store recovery codes privately before leaving the page.
- Availability: Consultations publishes explicit future start/end slots. Times are entered in the administrator browser's timezone, displayed in the visitor's timezone and stored in UTC. This is the internal Ochilink Hub calendar, not a Google/Outlook/legacy PHP Calendar synchronization. One host/calendar is supported.
- Booking: visitors can request an available slot or ask for a time by email. Slots are held for 30 minutes pending admin confirmation, not falsely marked confirmed. Database locking prevents overlapping slots and double bookings. Expired holds stop blocking availability without waiting for cleanup. Scheduled appointments continue blocking their slot.
- Emails: encrypted, deduplicated transactional outbox for request acknowledgments, optional admin notifications, consultation edits/cancellations, reset links, password-change alerts, payment links and payment receipts. Immediate sends are attempted during the initiating action. Pending/failed status and manual retry are visible in Settings. Provider acceptance is recorded as sent; it does not guarantee inbox delivery. Provider errors are redacted. No email is sent from developer tests.
- Payments: Admin can quote a consultation and email a payment link. The public payment view uses Stripe Checkout. Verified paid/refund events update the database and dashboard. Duplicate events do not double-count; mismatches fail for retry/review. Payments arriving after cancellation or a quote change are logged as PAYMENT_REQUIRES_REVIEW and still recorded as received.
- Consultation editing: client name/email, notes, quote, status and published appointment slot can be edited in the original Consultations section. Status/time edits queue notifications. Scheduled status requires a slot; occupied slots cannot be removed. Completed appointments retain their existing schedule. Paid quotes cannot be silently changed.

## Automated maintenance

vercel.json schedules /api/maintenance daily at 08:00 UTC in Production. The endpoint requires Authorization: Bearer CRON_SECRET. Immediate email sends do not wait for this schedule. Failed emails become eligible to retry after five minutes; retry execution occurs when maintenance or the authenticated Send pending emails control is invoked. The daily fallback is not a five-minute scheduler. For frequent unattended retries, configure an external scheduler to call this protected endpoint every five minutes or use an appropriate deployment plan/scheduler; no new paid service is provisioned.

A batch sends at most five messages. Delivery keys remain stable across retries and retries stop after ten attempts. Unsent reset emails older than 30 minutes are discarded because the token expired; request a new reset link. Other unsent encrypted payloads expire after 23 hours, inside the provider idempotency window. Sent bodies are erased. Cleanup removes expired sessions/tokens/rate counters, clears expired reservations/pending MFA secrets and enforces 90-day analytics/audit/error/outbox retention. Daily cron runs after production deployment; previews require the authenticated manual outbox control or a configured test scheduler.

## Acceptance checks before production

1. Original layout: confirm login, sidebar, cards, tables, themes and app modal. The stylesheet hash is checked automatically against the original. Full browser visual QA is still required on the preview.
2. Recovery: request a reset to your actual administrator email; confirm receipt, single use and 30-minute expiry; verify old sessions fail after reset.
3. MFA: enroll with an authenticator, save recovery codes, verify password-only login asks for a code and wrong/reused codes fail. Test one recovery code and safe disable/re-enrollment.
4. Availability: add a future slot; request it; verify a second booking is blocked. Confirm/reschedule/cancel it in Admin and verify notifications. Test with a different browser timezone.
5. Emails: confirm the verified sender delivers actual messages. Simulate a failure with test settings, check pending state, restore valid settings and send pending messages. Do not test bulk sending to real clients.
6. Analytics: decline and verify no analytics requests; allow and generate page/click/scroll events; confirm the original Analytics tabs show real values; revoke consent and verify collection stops.
7. Stripe: use a test consultation/quote, email yourself a link, complete Stripe's documented test-card checkout, verify the signed webhook updates Paid once, then test a refund and duplicate webhook replay. Verify the webhook is reachable through deployment protection. Do not use a live card for sandbox testing.
8. Maintenance: verify the protected endpoint rejects unauthenticated requests and the production cron has its CRON_SECRET configured.

Automated tests use embedded PostgreSQL, real bcrypt/TOTP/Stripe signature verification and jsdom-rendered React pages with mocked provider network calls. These establish local integration behavior, not actual Resend delivery or Stripe/Vercel reachability. ## Public booking acceptance

- Public URL is `/booking` on the current deployment host; the custom domain works after domain activation. Admin Consultations opens this in a new tab and can copy its URL.
- Add a future availability window in the timezone shown in admin. A session starts at that window's start; choose a window long enough for the desired 1/2/3-hour session. Public dates come exclusively from published database slots. New York labels account for daylight saving.
- Availability and admin consultation data refresh every 15 seconds. Booked/temporarily reserved slots are disabled publicly, with no customer identity exposed. Concurrent booking is checked under the existing database lock.
- A request persists name, email, service, optional phone, notes, duration and server-calculated quote. It reserves the slot for 30 minutes pending admin confirmation. Confirm it as Scheduled before the hold expires to retain it.
- Quoted totals are not revenue. Recorded paid revenue increases only after a verified payment. Existing Stripe activation remains necessary for payments.
- `/api/availability` exposes public GET and administrator-only mutations; `/api/consultations` uses the existing validated request flow. No additional migration is needed beyond 001–003.
